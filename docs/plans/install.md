# Easy installation implementation plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task by task. Steps use checkbox (`- [ ]`) syntax. This document is planning only. Leave this work uncommitted for the reviewer.

**Goal:** At public release, a friend installs agmen and agmend with one command, joins a project with one invite command, and gets a precise repair command from `agmen doctor` when something fails.

**Architecture:** Extend onboarding's release, installer, login, invite and setup work. Keep agmend as the sole per-user service. The desktop bundles agmend and agmen and may register its helper with consent; same-version services from another channel are reused. Add only the missing signature verification, install lifecycle, repository selection, diagnostics and private-preview instructions.

**Tech Stack:** The existing Rust workspace, POSIX sh, launchd on macOS, systemd user services on Linux, dist 0.33.1 as planned, and Homebrew. Proposed addition: Cosign for release signatures, subject to the verifier bootstrap check in Task I1. No new Rust dependency is assumed.

**Spec:** `docs/specs/2026-10-26-onboarding-and-hosting-design.md:108` describes join and setup; `docs/specs/2026-10-26-onboarding-and-hosting-design.md:129` describes distribution. This plan extends `docs/plans/onboarding.md:764` Tasks 13 and 14. Completion plan D37 controls the release shape (`origin/main:docs/plans/completion.md:73`). Automatic repository selection is a proposed spec amendment, not an approved behavior.

## Global Constraints

- Public-release target command: `curl --proto '=https' --tlsv1.2 -fsSL https://getagmen.ai/install.sh | sh`. Before publication, friends use the signed, notarized DMG and bundled CLI (desktop-install Decision 1 and Task 8); the shell installer and formula ship at public release. Alternative: `brew install agmen-dev/tap/agmen`. These are target experiences, not verified live endpoints. Install agmen and agmend from the same version. Do not install the hub, a broker, Docker or an agent for a joining friend.
- Initial daemon support means macOS with a GUI user session and Linux with a working systemd user manager. Service backends are selected at `origin/main:crates/agmend/src/service/mod.rs:91`. The current Linux code always selects systemd and propagates systemctl errors; shared Task S1 adds user-manager detection and an actionable unsupported-service result with the foreground `agmend` command. Do not promise universal Linux autostart. Preserve onboarding's Windows CLI work; do not claim Windows daemon support.
- Use the existing user service only. launchd writes `Library/LaunchAgents/dev.agmen.agmend.plist` (`origin/main:crates/agmend/src/service/launchd.rs:109`); systemd writes `.config/systemd/user/agmend.service` (`origin/main:crates/agmend/src/service/systemd.rs:138`). Do not also register a Homebrew-managed service.
- The site-hosted bootstrap script is initially trusted through HTTPS and the independently permissioned site repository. A compromised site or trust root can still replace the script and its published checksum; Cosign on release archives does not authenticate the script itself. A release checksum alone does not authenticate its author. I1 must verify a signature against a separately pinned signing identity before the shell installer extracts or executes installed binaries; the formula uses its protected publisher's sha256. Do not call checksum verification signature verification.
- Preserve identity trust, invite fragment handling and per-machine tokens from onboarding's constraints (`docs/plans/onboarding.md:25` and `docs/plans/onboarding.md:28`). No credentials in URLs, command output or receipts. Tests use temporary homes and token directories, not the user's keychain (`origin/main:crates/agmen-cli/tests/support/mod.rs:404`).
- Keep the existing noninteractive join behavior until Andy approves I3's spec amendment. The spec explicitly stops outside a clone (`docs/specs/2026-10-26-onboarding-and-hosting-design.md:112`), and Task 7 accepts the invite before that stop (`docs/plans/onboarding.md:510`). Changing this requires an explicit migration note and replacement of its documented test, not a silent rewrite.
- Every proposed operation has a bound: three download attempts at most per asset, 10 s connection and 600 s total per attempt; 120 s signature verification; 120 s total service transition including ready/version handshake; 300 s clone; 30 s total doctor run. Bound downloaded metadata to 1 MiB, archives to 512 MiB, diagnostic output to 64 KiB and a single diagnostic result to 512 characters. D-limits: both plans use 512 MiB archives, 600 s downloads and 120 s service transitions. Universal three-binary apps need more headroom than CLI archives, slow friend connections need 10 min, and service startup plus readiness needs one bounded 2 min deadline. Validate actual artifact sizes before shipping; these are ceilings, not measurements.

## Review Focus

1. Shell archives with invalid signatures, wrong workflow identity or missing signature bundle fail before extraction, replacement or service calls. Homebrew verifies its formula sha256, not Cosign; a mismatched archive fails before install. The site script has a separate HTTPS/site trust boundary. I1 tests all three contracts.
2. First install, repeat install, upgrade while agmend runs, interrupted replacement, and service start failure. Expected: both versions agree, a bounded health check confirms the new daemon, or schema-compatible rollback restores the prior pair and owned service; a schema bump keeps the new pair and reports failure. I2.
3. A single-use invite accepted before cloning fails. Expected: membership remains usable through `join --project`; no second acceptance is attempted. I3. Cover an absent repo URL, an existing destination and private-repo authentication failure.
4. Doctor with no daemon, missing sign-in, wrong local API version, HTTPS failure, broker failure and each unwired agent. Expected: independent failures remain visible; dependent checks say skipped with a reason. No automatic repair. I4.
5. A friend without source, tap, asset or marketplace access. Expected: the guide distinguishes all four permissions and never promises that a private tap alone grants release access. I5.

### Shared Task S1: agmend handshake, service ownership, restart and store safety

This is the single shared prerequisite for I2 and desktop-install Tasks 5, 6 and 11. Implement once, before either installer lifecycle.

**Files:**
- Modify: `crates/agmen-client/src/{paths.rs,lib.rs}` and its receipt tests, `crates/agmen-cli/src/cmd/mod.rs` and CLI receipt tests (one shared receipt reader), `crates/agmend/src/{main.rs,api.rs}`, `crates/agmend/src/service/{mod.rs,launchd.rs,systemd.rs}`, `crates/agmen-local/src/{message.rs,lib.rs}`, `crates/agmen-client/src/db.rs`, `crates/agmend/tests/{api.rs,cli.rs}`, `crates/agmen-client/src/error.rs`.

**Interfaces:**
- `hello {api: 1}` adds `version`, `build` (`AGMEN_BUILD` or `dev`) and `exe` (`current_exe()`), retaining `api`. Shared `HelloAnswer` keeps `api: u32` required and new fields optional for older daemons. This reports the running process, not the path a service will launch next.
- Add `agmend service status --json`: `{state, program}` with an absolute configured path or null when absent. Keep existing text status and its exit behavior unchanged. Read at most 64 KiB of plist `ProgramArguments[0]` or unit `ExecStart` without requiring a live process or an existing executable. Decode XML/systemd escaping; malformed or ambiguous configuration is an error, never permission to overwrite. This makes missing moved-app paths visible to both app and doctor.
- Add `agmend service install --program <absolute-path>` for a stable shell active link or Homebrew opt path. Validate the path and file, preserve its stable spelling rather than canonicalizing through it into a Cellar/version directory; default remains `current_exe()`. Do not infer ownership from the currently executing helper. Callers compare configured paths and receipts before mutation.
- Define the shell receipt as `state_dir()?.join("install-receipt.json")`, reusing `agmen_client::state_dir` (`origin/main:crates/agmen-client/src/lib.rs:38`, implementation at `origin/main:crates/agmen-client/src/paths.rs:43`). This is `~/Library/Application Support/agmen/install-receipt.json` on macOS and `${XDG_STATE_HOME:-~/.local/state}/agmen/install-receipt.json` on Linux; relative XDG paths use the helper's HOME fallback. Schema: `{channel, version, owned_paths[]}`, with absolute owned paths and no secrets. Add one bounded (64 KiB) typed receipt reader in agmen-client, exported for desktop, doctor and I2. Missing means no receipt; invalid or unreadable means an error and blocks ownership-changing writes. I2 writes atomically with mode 0600. No independent receipt path discovery or JSON parsers in consumers. Add proposed read-only `agmen install-receipt --json`, delegating to this reader, so I2's shell entry point can inspect the same file: present returns the receipt JSON, absent returns JSON null, both exit 0; malformed/unreadable returns nonzero. I2 calls the authenticated staged CLI before ownership changes; doctor and desktop call the Rust reader directly.
- Add `agmend service install --token-store-dir <absolute-path>`: validate an owner-only directory (0700; token files 0600), XML-escape `EnvironmentVariables` with `AGMEN_TOKEN_STORE_DIR` in the launchd plist and quote/escape `Environment="AGMEN_TOKEN_STORE_DIR=<path>"` in the systemd unit. The selected directory is explicit, never inferred from an interactive shell export. The desktop and CLI use the same directory when the person chooses this fallback. Preserve it on restart and rollback; never silently export existing Keychain tokens.
- `agmend service install` itself waits at most 30 s after manager start/restart for the daemon on its owned socket to answer `hello` with the installer's own release version and `ready`. This wait is inside the total 120 s transition deadline. Version mismatch fails immediately with expected and actual versions; timeout exits nonzero with "agmend did not become ready within 30 s" and the log path. Shell callers rely on this exit status, without implementing a local API client in sh.
- Add `agmend store-schema --json`: a read-only snapshot `{stores: [{path, schema_version}]}` for every daemon store, using read-only SQLite handles and `PRAGMA user_version`, never the migrating `Db::open`. Missing/unreadable stores, incomplete discovery or an unavailable snapshot return nonzero with context and block rollback. No create, migration, WAL setup, journal files or schema changes. I2 records this snapshot before activation and reads it again after failure, even if ready never arrived; compare the complete path/version set and allow rollback only when unchanged.
- Service install detects an active systemd unit, then daemon-reload, enable and restart; inactive units start. launchd retains bootout then bootstrap. Bound the entire transition to 120 s, including the 30 s ready/version handshake. Linux without a working user manager gets a precise error and foreground fallback. Current systemd start-only behavior is at `origin/main:crates/agmend/src/service/systemd.rs:50`; current executable capture is at `origin/main:crates/agmend/src/service/mod.rs:85`.
- Refuse a store with a newer schema before any write, journal-mode change or migration, with a clear version error. Reuse the existing `StoreVersion` error and version check (`origin/main:crates/agmen-client/src/db.rs:73`); that check currently follows WAL setup at `origin/main:crates/agmen-client/src/db.rs:65`, so strengthen it to guarantee no writes and recheck under the migration lock. Cover all stores opened by agmend. Add a backward-compatible `ready` local API answer reporting readiness and the store schema versions needed to decide rollback safety, once startup and stores are ready. `hello` alone is process identity, not store readiness.
